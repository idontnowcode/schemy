# ADR-014: Phase 5 — PCB·시뮬레이션·펌웨어를 「검증 방법 먼저」로 나누기

- 상태: **제안(Proposed)** — 사용자가 순서와 범위를 승인하기 전에는 구현하지 않는다(기획서 20장 4번).
- 날짜: 2026-11-06
- 관련: ADR-002(KiCad 버전), ADR-005(데이터시트), ADR-011(기술 검토), ADR-012(KiCad 수정 가져오기)

## 배경

기획서의 제품 비전은 하나의 입력 창에서 회로도·아트웍(PCB)·펌웨어를 다루는 것이다. Phase 0~4로 회로도 쪽(IR → KiCad 회로도, 제안·승인, 템플릿, Agent, 데이터시트 대조, 기술 검토, 설계 가이드)은 갖췄다. 기획서는 Phase 5의 각 기능을 「검증 방법을 정한 ADR 없이 구현하지 말 것」으로 묶어 두었다. 이 문서는 그 검증 방법과 순서를 제안한다.

이 환경의 KiCad 10.0.8(Docker `kicad/kicad:10.0.8`)에서 확인한 것(2026-11-06):

- `kicad-cli sch export netlist --format spice`가 있다(형식: kicadsexpr, kicadxml, cadstar, orcadpcb2, spice, spicemodel, pads, allegro).
- `kicad-cli pcb`는 `drc`, `export`(gerbers, drill, pos, ipc2581, odb, step, svg, pdf …), `import`, `render`, `upgrade`만 있다. **회로도에서 PCB를 갱신하는 명령은 없다.**
- 이미지에 `ngspice`(실행 파일과 libngspice)가 있고, 풋프린트 라이브러리 155개, `Simulation_SPICE` 심볼 라이브러리가 있다.
- LED 예제를 SPICE 넷리스트로 내보내 보았다. 그대로는 돌릴 수 없다:
  - 커넥터 J1은 모델이 없어 빈 줄(`J1 __J1`)이 되고, VIN을 공급하는 전원이 없다.
  - D1은 `D1 GND /LED_A LED`로 나온다. 정의되지 않은 모델 `LED`를 가리키고, 노드가 심볼 핀 순서(1=K, 2=A)여서 SPICE 다이오드(양극, 음극)로 읽으면 **거꾸로** 시뮬레이션된다. 심볼마다 핀 대응(`Sim.Pins`)과 모델이 있어야 한다.

## 제안

기능마다 「무엇을 맞다고 볼지」를 먼저 정하고, 작은 것부터 한다. 각 단계는 따로 승인받는다.

| 순서 | 기능 | 하는 일 | 맞다고 보는 기준(검증 방법) | 하지 않는 것 |
|---|---|---|---|---|
| 1 | **풋프린트·패드 확인** | 부품마다 IR의 풋프린트가 KiCad 라이브러리에 있는지, 심볼 핀 번호가 모두 패드 번호에 있는지 확인. 결과를 「검사」 탭과 BOM에 표시 | 예제 6개 + 일부러 틀린 풋프린트(없는 이름, 핀 수 부족)를 시험 데이터로. KiCad 라이브러리 파일을 직접 읽어 비교 | 풋프린트를 바꾸지 않음(바꾸는 것은 제안으로) |
| 2 | **SPICE: 직류 동작점·과도 응답** | 전원 Net 전압(IR 0.8 `voltage`)으로 전원을 넣고, 모델이 있는 부품만 넷리스트에 넣어 ngspice로 동작점(레일 전압, LED 전류)과 과도 응답(RC, 555 주기)을 계산 | 기술 검토의 손계산과 비교: LED 예제 전류 = (VIN − Vf) / R, NE555 예제 주기 = 0.693·(R1 + 2R2)·C. 차이가 5 % 안이면 통과. 모델이 없는 부품이 있으면 결과를 내지 않고 「모델 없음」으로 알림 | AI가 SPICE 모델을 쓰지 않음. 모델은 제조사 파일이나 KiCad `Simulation_SPICE`에서만. 모델 값을 지어내지 않음 |
| 3 | **PCB 시작 파일** | 회로도와 같은 넷으로 `.kicad_pcb`를 만들고 풋프린트를 회로도 블록별로 모아 놓기(배선 없음). 보드 외곽은 사용자가 크기를 정함 | KiCad에서 열림(재저장 무손실), `kicad-cli pcb drc`에서 「연결 안 됨」 외 오류 0, 패드-넷 대응이 IR 넷과 같음(IPC-D-356 내보내기로 비교) | 자동 배선(기획서 2장에서 제외), 부품 배치 최적화 |
| 4 | **펌웨어 핀 정의** | MCU 보드에서 IR의 핀-넷 연결로 핀 정의 헤더(예: `#define STATUS_LED PB5`)를 만듦 | 핀 이름을 데이터시트 요약의 핀 표와 대조, 제조사 툴체인(ATmega 예제는 avr-gcc)으로 빈 프로그램이 컴파일됨 | 주변장치 초기화 코드 생성, 실물 동작 확인(사람이 함) |
| 5 | **제조 파일** | 사람이 배선을 마친 PCB에서 Gerber·드릴·부품 위치 파일 내보내기 | `kicad-cli pcb export gerbers/drill/pos`가 오류 없이 끝나고, DRC 0, 층 수·파일 목록이 제조사 규칙 사전 설정과 맞음. 제조사 뷰어 확인은 사람이 함 | 제조 가능성 판정(사람·제조사가 함) |

공통 원칙(기존과 같음):

- 앱은 회로·보드를 직접 바꾸지 않는다. 결과는 보고서이거나, 바꾸는 것은 제안(proposal) → 승인으로만.
- KiCad CLI는 인자 목록으로 부르고, 결과 파일과 로그를 보드 폴더에 남긴다.
- 「통과」는 위 기준을 통과했다는 뜻일 뿐, 설계가 맞다는 뜻이 아니다. 실물 시험·엔지니어 검토 기록만이 「검토됨」을 만든다.
- 각 단계는 실제 KiCad 10.0.8로 확인한 결과를 ADR의 검증 절에 적는다(가짜 결과로 보고하지 않음).

## 사용자가 정할 것

1. 위 순서로 갈지, 먼저 할 것을 바꿀지(예: PCB보다 펌웨어 먼저).
2. 2단계에서 쓸 SPICE 모델의 출처(제조사 모델 파일을 받는 방법, 사내 모델 라이브러리가 있는지).
3. 3·5단계의 기준 PCB 규칙(층 수, 최소 선폭·간격, 자주 쓰는 제조사).
4. 4단계의 대상 MCU 계열과 툴체인(avr-gcc, arm-none-eabi-gcc, STM32CubeIDE 등).

## 검토한 다른 안

| 안 | 판단 |
|---|---|
| PCB 자동 배치·배선까지 한 번에 | 검증 기준을 세울 수 없고 기획서 2장에서 제외했다. 사람이 배선하고 앱은 시작 파일과 검사를 맡는다. |
| SPICE 넷리스트를 KiCad 출력 그대로 실행 | 위 확인대로 전원·모델·핀 순서가 빠져 결과가 틀린다(다이오드가 거꾸로). 앱이 전원을 넣고 모델·핀 대응이 없는 부품은 제외하고 알린다. |
| AI가 모델·펌웨어를 바로 작성 | 맞는지 확인할 방법이 없다. AI 결과는 제안·후보로만, 검증 기준을 통과한 것만 쓴다. |
| KiCad 플러그인(IPC API)으로 PCB 갱신 | KiCad 10의 새 API는 실행 중인 KiCad가 필요하다. 먼저 파일 생성과 CLI 검사로 하고, 필요하면 별도 ADR로 검토한다. |

## 남은 위험

- `.kicad_pcb` 생성은 회로도보다 형식이 크고 KiCad 버전에 민감하다. 3단계 전에 golden 파일과 재저장 무손실 시험을 회로도처럼 갖춰야 한다.
- 제조사 SPICE 모델은 형식(PSpice, LTspice 전용 문법)이 달라 ngspice가 못 읽을 수 있다. 못 읽으면 그 부품은 시뮬레이션에서 빠진다고 알린다.
- 펌웨어 핀 정의는 데이터시트 요약이 맞아야 맞다. 요약을 원문과 대조한 표시(「원문 확인함」)가 없으면 경고한다.
