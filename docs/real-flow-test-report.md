# 실제 흐름 시험 보고 — 24V CAN 온도 센서 노드 (2026-11-09)

사용자 요청: "네가 임의로 생성하는게 아니라, 실제 AI 모델로 돌려서 하나의 요구사항에 대한 진행 흐름대로 테스트를 해보고 디버깅 포인트를 찾아봐. 각 흐름 별로 캡쳐하면서." 이어서 "AI 모델 동작은 네가 대신 해."

## 방법

- 앱(백엔드 + 화면)을 그대로 띄우고, AI 공급자 자리에 중계 공급자(`tests/relay_backend.py`)를 넣었다. 앱이 보내는 프롬프트를 파일로 받아 Claude(이 세션)가 읽고 답을 써서 돌려준다. 미리 짠 각본은 없다.
- KiCad 10.0.8 공식 Docker 이미지로 ERC·Netlist를 실제로 돌렸고, 부품 해석은 그 이미지의 전체 심볼 라이브러리(224개)로 했다.
- 화면은 Playwright로 조작하며 단계마다 캡처했다. 캡처와 상세는 보고서 페이지(대화에 공유된 링크)에 있다.

요구사항: 24 V(18~32 V) 입력, STM32(CAN 내장)·SWD, CAN 트랜시버·점퍼 종단, 24 V → 3.3 V 강압·역전압·서지 보호, I2C 온도 센서, LED 2개, 4핀 단자대. AI 질문 답: 500 kbps, 24 V에서 50 mA 이하, 3.3 V 트랜시버, IEC 61000-4-5 ±1 kV · −40~85 °C, 절연 필요 없음.

## 결과

- 7단계 완주. AI 호출 8회(정리 1, 부품 계획 1, 연결 1, 검토 3, 수정안 편집 2). 제안 3개, #2 승인 → revision 1.
- 부품 39개 모두 KiCad 10 심볼로 해석, 연결 1회 통과, 지침 자동 점검 위반 없음, ERC 0/0, Netlist 일치.
- AI 검토 수정 권장 2개(벅 2.1 MHz 최소 온타임, 입력 감쇠 콘덴서) 모두 근거 확인됨 → 고칠 곳만 편집 15개로 수정안 #2 → 2회차 권장 1개에서 조건 충족으로 멈춤.

## 한계

- AI 역할은 Claude가 맡았다. 다른 모델(Gemini Flash 등)은 형식·핀·근거에서 더 자주 틀릴 수 있다. 「AI 성능 평가」로 실제 모델을 재야 한다.
- 고친 것은 테스트(pytest, vitest, e2e)와 같은 revision 재생성으로 확인했다. 7단계 전체를 다시 돌리지는 않았다.

# 두 번째 실제 흐름 시험 — 0~10 V 입력 RS-485 모듈 (2026-11-09)

사용자 요청: "다시, 다른 케이스로 한번 더 진행하면서 기록해봐. 억지로 수정사항을 만들 필요는 없고, 수정이 필요한 부분은 반드시 짚고 넘어가줘."

첫 시험과 다른 경로를 타도록 골랐다: ATmega328P(5 V, MCU 템플릿 후보), 0~10 V 아날로그 입력과 24 V 오배선 보호, RS-485와 딥스위치 종단, 5.08 mm 단자대, **보유 자재 목록(CSV 30종)을 먼저 쓰기**. AI 질문 답: 풀스케일 ±1 %·10 Hz, 19200 bps, 바이어스는 마스터 쪽, 24 V에서 40 mA 이하·−20~70 °C.

## 결과

- 7단계 완주 + 사람이 회로 데이터에서 고쳐 revision 2. AI 호출 8회(정리 1, 부품 계획 1, 연결 1, 지침 점검 편집 1, 검토 2, 수정안 편집 2(새 부품 핀 표로 한 번 고침 포함)).
- 부품 41개(템플릿 LM2596 벅 포함) 해석, 32개가 보유 자재 품번으로 들어감. 연결 1회 통과, ERC 0/0, Netlist 일치(revision 1·2 모두).
- 지침 자동 점검이 위반 3개를 찾았고, AI가 맞는 2개(LM2596 입력 세라믹)는 고치고 틀린 1개(G-MCU-04)는 이유와 함께 거절 → 3 → 0.
- 자동 반복 검토: 1회차 의견 3개 → 수정안 #2(J4 교체, SM712 3핀으로 교체, TVS 문제는 사람 판단으로 남김) → 2회차에 같은 의견(J5 풋프린트)이 다시 나와 멈춤(무한 반복 없음).
- 남은 풋프린트 문제는 사람이 고급 화면 「회로 데이터」에서 고쳐 revision 2 → 「회로도 다시 만들기」 → ERC 0/0.
